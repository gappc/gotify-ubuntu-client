# Gotify tray client for Ubuntu — design

Date: 2026-11-05
Status: draft for review

## Why

The user gets server deployment and status notifications through a
self-hosted Gotify server. Android works (official Gotify app), but their
Ubuntu desktop has no Gotify integration at all. We looked at replacing
Gotify with MQTT and decided against it: Gotify already provides message
history and the Android client, so the only missing piece is a desktop
client.

Today, all messages come from **Uptime Kuma** (one Gotify application,
~150 messages since April 2026, about 5 a week). The client must make the
difference between "something went down" and "it's back up" obvious, and
show at a glance whether anything is down *right now*.

## Goals

1. Small background app for Ubuntu (GNOME) that stays connected to one
   Gotify server and shows desktop notifications for new messages.
2. Tray icon with a menu that shows connection state and which Uptime Kuma
   monitors are currently down.
3. A message window similar to the Gotify Android app: read messages,
   filter by application, delete messages, open links.
4. Login and connection settings inside the app (no hand-edited config
   needed).
5. **Very low resource use** while idle, and fast. This is an explicit
   user requirement.

## Non-goals

- Sending messages, or creating/managing Gotify applications, users or
  plugins (stays in Gotify's web UI).
- Multiple Gotify servers or accounts.
- OIDC login (the user's server has OIDC disabled; see "Later").
- Markdown rendering, images, `extras` actions (none of the user's messages
  use them).
- Other desktops than GNOME on Ubuntu, other distros, packaging as `.deb`,
  Flatpak or Snap.

## Anti-goals (would make this a failure even if it works)

- A background process that uses tens of MB of memory or wakes the CPU
  regularly while nothing happens.
- Success messages ("Up") that stay on screen like failures.
- A red tray icon that gets stuck red with no way to clear it.
- Losing messages silently after a network drop or suspend/resume.
- Storing the Gotify password, or storing the token in plain text.

## Constraints and facts

- **Language:** Rust (user's choice). Toolchain on the machine:
  rustc/cargo 1.99.1.
- **Desktop:** Ubuntu with GNOME Shell 50.1 and the `ubuntu-appindicators`
  extension enabled (so StatusNotifierItem tray icons work). GTK 4.22 and
  libadwaita 1.9 are installed.
- **Network:** the server is reached over public HTTPS with a publicly
  trusted certificate (verified). No custom CA or self-signed support
  needed; plain HTTP need not be supported. Unreachable = normal
  "Reconnecting…" with backoff.
- **Login session:** no GDM auto-login, and the GNOME login keyring is
  unlocked at session start (verified). If the keyring is still locked or
  unavailable at startup, wait quietly (grey icon, "Waiting for keyring")
  and retry when it unlocks; never pop up an unlock prompt by itself.
- **Server:** Gotify 3.1.0. `GET /gotifyinfo` reports `localAuth: true`,
  `oidc: false`, `register: false`. The server's API spec is available at
  `GET /swagger`.
- **Gotify 3 API details that matter:**
  - `GET /message` and `GET /application/{id}/message` accept `limit` of
    at most **200** (400 error above). Page with `since` (ID of the last
    message returned) or `paging.next`, which is now a **relative** path
    and must be prefixed with the base URL. Messages come newest first.
  - Live messages: WebSocket `GET /stream` (client token via
    `X-Gotify-Key` header, `Authorization: Bearer`, or `?token=`). The
    stream only sends *new* messages; there are no deletion events.
  - Creating a client token: `POST /client` with HTTP Basic auth and body
    `{"name": ..., "expiresAfterInactivitySeconds": ...}`. The token is only
    returned in this response (GET endpoints no longer return tokens).
    `expiresAfterInactivitySeconds` omitted or 0 means never expires.
  - With a plain (non-elevated) client token, `DELETE /client/{id}` returns
    403. Basic-auth requests are always elevated.
  - Message deletion: `DELETE /message/{id}`, and
    `DELETE /application/{id}/message` for all messages of one app. Both
    work with a normal client token.
  - App icons: `Application.image` is a relative path (e.g.
    `image/abc.png`); the default icon is a generic path containing
    `static/defaultapp.png`.
- **Uptime Kuma's Gotify sender** (`server/notification-providers/gotify.js`
  upstream): title is always `Uptime-Kuma`, priority is one fixed value per
  notification channel (default 8), and the message text is generated by
  Kuma in a fixed format. In the user's data, 151 of 152 messages match:
  - `[<monitor name>] [🔴 Down] <details>`
  - `[<monitor name>] [✅ Up] <details>`
  Up and Down messages both arrive with priority 8, so **priority alone
  cannot tell them apart.**

## What it does (decided with the user)

### Notifications

- Uptime Kuma messages (matched by the pattern above):
  - **Down** → notification stays on screen until dismissed (GNOME
    "critical" urgency).
  - **Up** → normal notification that fades away.
  - Title shown is the **monitor name** (not "Uptime-Kuma"), with a clear
    down/up marker.
  - **When a monitor comes back up, its Down notification is replaced** by
    the Up one (same notification id via `replaces_id`), so no stale
    "down" banner stays on screen after recovery (my call). This requires
    tracking the notification id per monitor and dropping it on
    `NotificationClosed`; Down notifications that were folded into a
    missed-messages summary are not replaced.
- All other messages follow Gotify priority, the same ranges as the
  Android app:

  | Priority | Notification |
  |---|---|
  | 8–10 | stays on screen (critical urgency) |
  | 4–7 | normal, fades |
  | 1–3 | low urgency (no banner; only in GNOME's notification list) |
  | 0 | no notification; only in the message window |

- Clicking a notification opens the message window at that message.
- If the message contains a URL, the notification gets an "Open link"
  action.
- After a disconnect (network drop, suspend), the app reconnects on its own
  and fetches what it missed from the server. If more than one message was
  missed, show **one summary notification** ("5 missed messages") instead
  of one per message. If any missed message is a Down or priority ≥ 8, the
  summary stays on screen.

### Tray icon and menu

- Icon states:
  - normal: connected, nothing down
  - **red: at least one Uptime Kuma monitor is down right now**
  - grey: not connected or not configured
  - plus a dot/badge when there are unread messages
- Menu:
  - Status line ("Connected to gotify.example.com" / "Reconnecting…" /
    "Not configured")
  - "Down right now" section: one entry per down monitor, e.g.
    `web01 — down since 14:32`. Clicking it opens the message window at the
    Down message. Each entry offers **Clear** (for monitors that were
    deleted or renamed in Kuma and will never send "Up").
  - Show messages
  - Settings
  - Quit
- Left click on the icon opens the menu (matching the user's voice
  assistant project).

### "Down right now" state

- For each monitor name, the newest Kuma message decides (Down → down,
  Up → up). Live messages update it immediately.
- **Deletions only ever clear a monitor, never make it down again** (my
  call). The app keeps the last known state per monitor in its state file.
  A monitor is down only if its newest *known* event is Down **and** that
  Down message still exists on the server. So deleting a Down message
  (e.g. on Android) clears it, while tidying away Up messages does not
  revive an old outage.
- Re-sync with the server (page through the full history; ~150 messages
  today, so this is cheap) at startup, after every reconnect, when the
  window process exits, **when the tray menu is opened**, and as a fallback
  **every 15 minutes** (my call: the stream has no deletion events, and a
  few requests every 15 minutes is negligible next to the keepalive).
- "Clear" hides a monitor from the down list until a newer message for that
  monitor arrives. Cleared monitors are kept in the local state file.

### Message window

Modelled on the Gotify Android app:

- Sidebar with "All messages" and one entry per Gotify application (icon if
  the app has a custom one, unread count). **Hidden while there's only one
  application** (my call; the user has one today).
- Message list, newest first: app, title (monitor name for Kuma messages,
  with red/green marker), text, relative time ("5 min ago"), coloured
  marker for priority ≥ 8. More history loads when scrolling down (pages of
  200).
- Plain text only; URLs are clickable and open in the default browser.
- Delete button on each message, and "Delete all" for the selected app.
  Deletes happen on the server, so they also disappear on Android.
- New messages appear live while the window is open.
- Read state is local (Gotify has none): opening the window marks
  everything up to the newest message as read and clears the tray badge.

### Settings and login

- Fields: server URL, username, password. "Test connection" button
  (calls `/version` and `/gotifyinfo`).
- Login creates a client token with `POST /client` (Basic auth), named e.g.
  `Ubuntu tray (<hostname>)`, with `expiresAfterInactivitySeconds` omitted
  (never expires).
- The password is never stored. The token is stored in the GNOME keyring
  (Secret Service); server URL and client id go in a small config file.
- When logged in, Settings shows the server and user and a **Log out**
  button. Log out removes the local token and tries `DELETE /client/{id}`;
  since that needs an elevated session it will usually get 403, in which
  case the app says to remove the client in Gotify's web UI.
- If the server rejects the token (401, e.g. client deleted in the web
  UI), the app goes to the grey "not configured" state and shows one
  notification asking to log in again.

### Start, install, single instance

- `cargo build --release`, plus an install script that copies the binary to
  `~/.local/bin`, installs a `.desktop` file (app menu) and an autostart
  entry (`~/.config/autostart`). No `.deb`.
- Only one instance runs. Launching it again (e.g. from the app menu) opens
  the message window instead.

## Resource budget and the shape that follows from it (my call)

Requirement: the always-running part must stay tiny. GTK, once loaded into
a process, stays loaded even after its windows are closed, and costs tens
of MB. So:

- **Background process** (always running): Gotify connection, tray icon
  (StatusNotifierItem over D-Bus, e.g. `ksni`), notifications
  (org.freedesktop.Notifications over D-Bus, e.g. `notify-rust` or
  directly with `zbus`), down-state, read state. **No GTK.**
  Target: **≤ 15 MB resident memory** and no periodic wakeups while idle
  beyond the WebSocket keepalive and the 15-minute re-sync.
- **Window process** (same binary, started on demand, e.g.
  `gotify-tray window [--message <id>]`): GTK4 + libadwaita message window
  and settings. It reads the token from the keyring and talks to Gotify
  directly. It exits when its window closes, freeing all GTK memory.
- The background process re-syncs from the server when the window process
  exits (covers deletions and logins done in the window). Settings changes
  (login/logout) must take effect in the background process without a
  restart.
- Single-instance check and "open the window" requests go through the
  background process (e.g. a well-known D-Bus name or a Unix socket); only
  one window process at a time.

## Local files

- Config: `~/.config/gotify-tray/config.toml` — server URL, client id.
- State: `~/.local/state/gotify-tray/state.json` — last read message id,
  last notified message id, last known state per monitor (with the message
  id of that event), cleared monitors.
- Token: GNOME keyring only.

## Robustness

- Reconnect with backoff (e.g. 1 s, doubling, capped at ~60 s); reconnect
  immediately when the network comes back or the machine resumes from
  suspend (logind `PrepareForSleep` / NetworkManager signals), since a
  WebSocket can sit half-dead after resume.
- Keep a "highest message id seen" so missed messages are found by paging
  `GET /message` until reaching it. This also covers the time the app was
  not running: on startup, messages newer than "last notified id" produce
  the missed-messages summary. On the very first run, history is not
  notified.

## Left to the builder

- Crate choices (async runtime or not, HTTP/WebSocket client, keyring
  crate, TLS backend), as long as the resource budget holds.
- How the background and window processes talk to each other.
- Tray icon artwork (drawn at runtime or embedded) and exact visual design
  of the window, within libadwaita conventions.
- Binary/app name (`gotify-tray` is a placeholder) and the app ID.
- Exact Kuma pattern regex (must handle `]` inside monitor names reasonably)
  and how monitor identity is keyed.
- Test approach: unit tests for Kuma parsing, priority mapping, down-state
  computation and missed-message logic; a local Gotify 3 instance (e.g.
  Docker) for end-to-end checks. Never write to the user's real server
  during development without asking.

## Things to verify early

- GNOME 50: critical-urgency notifications stay until dismissed and are
  shown during Do Not Disturb (assumed, not verified).
- Notification actions ("Open link", click to open window) work under
  GNOME with the chosen notification crate while the app runs in the
  background.
- Whether an open `/stream` WebSocket counts as client activity in Gotify 3
  (only matters if a client expiry is ever set; this design sets none).

## Later (not now)

  (`POST /auth/oidc/external/authorize` + `/auth/oidc/external/token`,
  PKCE, redirect URI).
- Markdown messages (`client::display` → `text/markdown`), images, actions.
